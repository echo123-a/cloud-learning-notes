## 1. 阶段一：本地环境与网络基础

### 1.1 Git 与 GitHub 配置
*   **本地 Git 配置**：配置 `user.name` 和 `user.email`，解决 `Author identity unknown` 报错。
*   **SSL 证书报错**：开启 Watt Toolkit 加速后，`git clone` 报 `SSL certificate problem`。解决：`git config --global http.sslbackend schannel`（让 Git 信任 Windows 系统证书库）。
*   **凭据认证**：`git push` 弹出 GitHub 授权窗口，选择 `Sign in with your browser`。
*   **中文乱码补丁**：`git config --global core.quotepath false`。

### 1.2 云服务器 (ECS) 网络基础
*   **出网不通**：购买实例时未分配公网带宽（峰值为 0）。解决：控制台修改带宽为按流量计费，峰值 5Mbps。
*   **入网不通**：云厂商的“安全组”拦截。解决：在安全组入方向手动放行特定 TCP 端口（如 80、5000、8080），授权对象 `0.0.0.0/0`。
*   **抓包实战**：使用 `tcpdump -i any -nn port 80 -S` 抓取 HTTP 请求。
    *   `[S]`：SYN 包（请求连接）
    *   `[S.]`：SYN+ACK（同意连接）
    *   `[.]`：ACK（确认收到）
    *   `[F.]`：FIN（断开连接）
*   **面试题：为什么是三次握手？** 为了确认双方的发送和接收能力都正常，防止历史失效的 SYN 包突然到达服务端导致资源浪费。

## 2. 阶段二：Linux 服务与故障排查

### 2.1 服务管理 (systemctl)
*   查看服务状态：`systemctl status nginx`（关注 `Active: active (running)` 或 `inactive (dead)`）。
*   启动/停止/重启/开机自启：`systemctl start/stop/restart/enable nginx`。

### 2.2 故障排查三层逻辑（面试必考：网站挂了怎么查？）
1.  **查服务状态**：`systemctl status 服务名`（看进程是否存活）。
2.  **查端口监听**：`ss -tlnp | grep 端口号`（看服务是否真正绑定了端口）。
3.  **查错误日志**：`tail -n 20 /var/log/...`（看具体报错原因）。

### 2.3 磁盘满了排查
*   `df -h`：看整体磁盘使用率。
*   `du -sh /*`：看根目录下哪个文件夹最占空间。
*   `du -sh /var/log/*`：深入查日志文件（清理日志用 `> 文件名` 清空，慎用 `rm` 防句柄丢失）。

## 3. 阶段三：Docker 容器化部署

### 3.1 Docker 基础与安装
*   **国内安装避坑**：使用官方脚本 `get.docker.com` 容易超时，改用阿里云软件源安装。
*   **镜像加速**：修改 `/etc/docker/daemon.json`，配置公共加速器（如 `docker.1ms.run`），重启 Docker 生效。

### 3.2 Dockerfile 编写规范与分层缓存
*   **标准结构**：`FROM` -> `WORKDIR` -> `COPY requirements` -> `RUN pip install` -> `COPY . .` -> `EXPOSE` -> `CMD`。
*   **分层缓存机制（面试高频）**：先拷贝 `requirements.txt` 并执行安装，再拷贝全量代码。这样只要依赖不变，修改代码重建镜像时会命中缓存，大幅提升构建速度。
*   **端口声明**：`EXPOSE` 仅是声明，真正开放端口靠 `docker run -p 宿主机端口:容器端口`。
*   **0.0.0.0 绑定**：容器内应用必须绑定 `host='0.0.0.0'`，否则外部流量无法进入容器。

### 3.3 传统部署 vs 容器化部署
*   **传统 systemd**：环境依赖容易冲突，无法做到“一次构建，到处运行”。
*   **容器化部署**：打包代码和运行环境，进程隔离，是云原生绝对主流。

## 4. 阶段四：K3s 集群部署与资源调优

### 4.1 解决 K3s 镜像拉取 403 Forbidden
*   **现象**：`kubectl get pods -A` 发现组件卡在 `ImagePullBackOff`，日志提示 `ntoomanyrequests`。
*   **根因**：K3s 底层使用 containerd，不读 Docker 的镜像加速配置，且公共免费加速器被限流。
*   **解决（离线导入法）**：
    1. 用 Docker 拉取镜像（借助 Docker 配好的加速）。
    2. 导出到 K3s 的自动导入目录：`docker save <image> -o /var/lib/rancher/k3s/agent/images/xxx.tar`
    3. 重启 K3s 触发自动导入：`systemctl restart k3s`。
    4. 验证：`k3s crictl images`（不能用 docker images 查）。

### 4.2 2核2G 服务器跑 K8s 的资源调优（高分面试题）
*   **现象**：`kubectl` 报 `TLS handshake timeout`，系统日志频繁报 `Slow SQL` 和 `Housekeeping took longer than expected`。
*   **根因**：2G 物理内存耗尽，触发 Linux OOM Killer，导致 kubelet 被卡死；Swap 未启用。
*   **调优手段**：
    1. **配置 Swap**：`sysctl vm.swappiness=60`，让系统积极使用虚拟内存，防 OOM。
    2. **裁剪组件**：删除不需要的 `metrics-server` 和 `svclb-traefik`。
    3. **卸载 Docker**：镜像导入 K3s 后，停止 Docker 服务 (`systemctl stop docker`)，彻底释放内存。

### 4.3 K8s 核心对象
*   **Pod**：K8s 最小调度单位，包含一个或多个容器。
*   **Deployment**：管理 Pod 副本数，实现故障自愈（Pod 挂了自动拉起）。
*   **Service**：给 Pod 提供固定访问入口。
    *   `ClusterIP`：仅集群内部访问。
    *   `NodePort`：在宿主机开放一个随机高位端口（30000-32767），外部通过 `IP:NodePort` 访问。
*   **YAML 关键配置**：`imagePullPolicy: IfNotPresent` 让 K8s 优先使用本地镜像。

## 5. 阶段五：K8s Ingress 前后端分离架构实战

### 5.1 项目架构说明
本项目模拟企业级云原生部署架构，将前端（静态页面）与后端（Python Flask API）分离部署，统一通过 K3s 的 Ingress (Traefik) 网关对外暴露服务。

**流量访问链路：**
`用户浏览器 (公网 80 端口) -> 阿里云安全组 -> 宿主机 svclb-traefik (iptables 转发) -> Traefik Ingress 路由 -> 对应的 K8s Service (ClusterIP) -> 后端 Pod (容器端口)`

### 5.2 核心技术点
*   **ConfigMap 挂载**：将 HTML 代码挂载到 Nginx 容器中，实现代码与镜像解耦，修改页面无需重建镜像。
*   **路径路由**：访问 `/` 转发给前端 Service，访问 `/api` 转发给后端 Service。
*   **字符编码**：在 HTML 的 `<head>` 中加入 `<meta charset="UTF-8">` 防乱码。

### 5.3 面试高频 Q&A
*   **Q：为什么要用 Ingress 而不是直接暴露 NodePort？**
    A：NodePort 会占用宿主机大量高位端口，且不支持基于域名或路径的路由。Ingress 作为七层网关，可以通过一个 80/443 端口统一接管流量，实现灵活的路径路由、SSL 卸载和灰度发布。
*   **Q：ConfigMap 挂载静态文件的好处是什么？**
    A：实现了配置与镜像的解耦。修改前端页面只需修改 ConfigMap 并重启 Pod，无需重新构建和推送 Docker 镜像，极大提升了开发和运维效率。

## 6. 附录：全链路排障手册（Troubleshooting Manual）

### 6.1 浏览器访问公网 IP 出现 ERR_CONNECTION_TIMED_OUT
*   **排查路径**：
    1. 检查阿里云安全组：确认入方向已放行 TCP 80 端口。
    2. 检查本地回环：在服务器执行 `curl -I http://127.0.0.1`，返回 `200 OK` 且带有 `Server: nginx/1.31.9` 标识。
*   **根因定位**：宿主机上遗留了之前测试用的**原生 Nginx 进程/容器**，抢占了 80 端口。导致 K3s 的 `svclb-traefik` 无法接管流量，公网请求到达网卡后被原生 Nginx 拦截，造成超时。
*   **解决方案**：`systemctl stop nginx` 停掉原生 Nginx，`systemctl disable nginx` 禁止自启。重启 K3s (`systemctl restart k3s`)，让 Traefik 重新接管宿主机 80 端口。

### 6.2 Traefik Ingress 控制器失踪
*   **现象**：`svclb-traefik` 在运行，但 `traefik` 的 Pod 不见了，Ingress 路由不生效。
*   **根因**：之前为了省内存手动删除了 Traefik 的 Deployment，导致 Helm 状态异常。
*   **解决**：删除 HelmChart 记录 (`kubectl delete helmcharts -n kube-system traefik`)，重启 K3s 让其自动重建控制器。

### 6.3 Docker 构建镜像报错找不到包版本
*   **报错现象**：`ERROR: Could not find a version that satisfies the requirement flask==2.3.3 (from versions: none)`
*   **根因**：Dockerfile 中指定了清华 PyPI 镜像源，但该源存在同步延迟，尚未收录该特定版本。
*   **解决**：将 Dockerfile 中的 pip 源更换为阿里云源 `https://mirrors.aliyun.com/pypi/simple/`。

### 6.4 网页前端中文显示乱码
*   **报错现象**：网页能打开，但中文变成“鎴戞槸鍓嶇鏂囦欢”等乱码。
*   **根因**：浏览器无法推断 HTML 的字符集编码，用错误编码（如 GBK）解析了 UTF-8 内容。
*   **解决**：在 HTML 文件的 `<head>` 中加入 `<meta charset="UTF-8">`。

### 6.5 K3s 系统组件卡在 ImagePullBackOff (403 Forbidden)
*   **现象**：执行 `kubectl get pods -A`，全卡在拉取镜像阶段，日志提示 `ntoomanyrequests: 免费节点当前繁忙`。
*   **解决（离线导入法）**：Docker 拉取镜像 -> 导出 tar 包 -> 放入 `/var/lib/rancher/k3s/agent/images/` -> 重启 K3s 自动导入。

## 7. Linux 核心基础命令与排障思维复习

### 7.1 日常巡检与资源查看
*   **内存与 Swap**：`free -h`（看内存是否耗尽，Swap 有没有用起来）。
*   **磁盘空间**：`df -h`（看各个挂载点的使用率）。
*   **目录大小**：`du -sh /*` 或 `du -sh /var/log/*`（逐层定位大文件）。
*   **系统负载与进程**：`top` 或 `htop`（实时看 CPU、内存占用，按 `q` 退出）。

### 7.2 文件与日志查看
*   **查看文件内容**：`cat filename`。
*   **看文件尾部**：`tail -n 20 xxx.log`（查最后 20 行报错）。
*   **实时滚动看日志**：`tail -f xxx.log`（盯日志最常用）。
*   **搜索关键字**：`grep "ERROR" xxx.log`。

### 7.3 网络与端口排障（重点）
*   **查看端口监听**：`ss -tlnp | grep :80`（查某个端口被谁占用了，是否正常 LISTEN）。
*   **测试连通性**：`ping -c 3 223.5.5.5`（测试网络层）。
*   **测试 Web 服务**：`curl -I http://127.0.0.1`（看 HTTP 响应头，排查应用是否存活）。
*   **抓包分析**：`tcpdump -i any -nn port 80 -S`。

### 7.4 服务与进程管理
*   **服务状态**：`systemctl status <服务名>`（看 Active 状态）。
*   **启停与自启**：`systemctl start/stop/restart/enable <服务名>`。
*   **查看服务系统日志**：`journalctl -u <服务名> -n 50`。
*   **查找进程**：`ps aux | grep <进程名>` 或 `ps -ef | grep <进程名>`。
*   **杀掉进程**：`kill -9 <PID>`（慎用，尽量先尝试正常 `kill PID`）。

### 7.5 面试标准排查思维（STAR 法则）
**遇到“网站打不开”，标准排查路径：**
1.  **查服务状态**：`systemctl status nginx`（服务是不是挂了？）。
2.  **查端口监听**：`ss -tlnp | grep :80`（服务活着但没监听端口？）。
3.  **查日志**：`tail -n 50 /var/log/nginx/error.log`（到底报了什么错？）。
4.  **查网络/外部**：本地 `curl` 通不通？云厂商安全组放行了吗？

## 8. 网络底层原理与 TCP 状态机

### 8.1 IP 地址 vs MAC 地址（面试高频）
*   **IP 地址**：负责**全局路由**（起点到终点）。在数据包传输过程中，**源 IP 和目的 IP 永远不变**。
*   **MAC 地址**：负责**局部交付**（当前一跳给下一跳）。在局域网内，路由器/交换机依靠 MAC 地址进行物理寻址。
*   **区别**：每经过一个路由器，MAC 地址会被重写，但 IP 地址不变。IP 是宏观的，MAC 是微观的。

### 8.2 为什么是“三次握手，四次挥手”？
*   **三次握手（建立连接）**：为了双向确认双方的**发送能力**和**接收能力**。服务端在第二次握手时，把“确认”和“询问”合并（SYN+ACK），所以省了一次。
*   **四次挥手（断开连接）**：因为 TCP 是**全双工**的，A 不发了不代表 B 也不发了。A 发送 FIN 后，只能表示 A 的单向通道关闭；必须等 B 把剩余数据发完，B 也发送 FIN，双方通道才算完全关闭。

### 8.3 关键 TCP 状态与生产排障（极深考点）
*   **CLOSE_WAIT**：被动关闭方（服务端）收到 FIN 后，发送 ACK 的状态。如果服务器上出现**大量 CLOSE_WAIT**，通常是因为**应用代码存在 Bug**，忘记调用 `close()` 释放连接。
*   **TIME_WAIT**：主动关闭方（客户端）发送最后一个 ACK 后，会等待 2MSL（最长报文段寿命，通常是 2-4 分钟）才彻底关闭。目的是为了确保服务端收到了最后的 ACK，以及让网络中延迟的旧数据包消散。高并发服务器常通过修改内核参数（`tcp_tw_reuse` 等）来优化 TIME_WAIT 过多的问题。

### 8.4 子网掩码（CIDR）与 VPC 网段规划
*   `/24`：包含 256 个 IP（可用 254 个），如 `192.168.1.0/24`。
*   `/16`：包含 65536 个 IP，如 `192.168.0.0/16`。
*   **云上实战**：创建 VPC 时，根据业务规模选择网段。网段划分过大可能造成浪费，过小可能不够用。

## 9. HTTP 协议基础与代理架构

### 9.1 HTTP 报文结构
*   **客户端请求（Request）**：包含请求行（如 `GET / HTTP/1.1`）、请求头（Headers，如 `Host`、`User-Agent`）、请求体（Body，如表单数据）。
*   **服务端响应（Response）**：包含状态行（如 `HTTP/1.1 200 OK`）、响应头（Headers，如 `Content-Type: text/html`、`Server: nginx`）、响应体（Body，即 HTML 代码）。

### 9.2 常见 HTTP 状态码（排障必考）
*   **200 OK**：请求成功。
*   **301 / 302**：重定向（301 永久，302 临时）。
*   **403 Forbidden**：权限不足，禁止访问。
*   **404 Not Found**：请求的资源（路径）不存在。
*   **500 Internal Server Error**：服务器内部代码错误（如 Python 程序抛异常）。
*   **502 Bad Gateway**：网关错误（Nginx 正常，但背后的应用挂了，连不上）。
*   **504 Gateway Timeout**：网关超时（Nginx 连上了后端，但后端迟迟不返回数据，超时了）。

### 9.3 正向代理与反向代理
*   **正向代理（代理客户端）**：客户端知道自己要访问谁，但通过代理去访问。服务端不知道真实客户端是谁。例如：翻墙工具、Watt Toolkit。
*   **反向代理（代理服务端）**：客户端以为代理就是真实服务器，但其实代理把请求转发给了内部真正的服务器。服务端隐藏在代理后面。例如：Nginx、K8s Ingress (Traefik)。

### 9.4 Nginx 为什么快？（异步非阻塞 I/O）
*   Nginx 采用 `epoll`（Linux 下高性能多路复用 I/O 模型），使用单线程或少量工作线程就能处理成千上万的并发连接，而不用像传统服务器那样每个连接分配一个线程（极其耗费内存）。

## 10. 容器底层原理与 K8s 核心架构

### 10.1 容器 vs 虚拟机
*   **虚拟机（VM）**：硬件级虚拟化。包含完整的 Guest OS，启动慢、资源开销大、隔离性极强。如阿里云 ECS。
*   **容器（Container）**：操作系统级虚拟化。**共享宿主机内核**，无需重装系统，启动极快（秒级），资源占用极小。
*   **核心隔离机制（Linux 内核）**：
    *   **Namespace（命名空间）**：实现资源隔离。让容器内的进程只能看到自己所在的网络、进程、挂载点（做到“各回各家”）。
    *   **Cgroups（控制组）**：实现资源限制。限制容器能使用的 CPU、内存、磁盘 I/O 上限（防止单容器把宿主机拖死）。

### 10.2 K8s 核心概念：为什么需要 Pod？
*   **Pod 是 K8s 最小的调度单位**，可以包含一个或多个紧密相关的容器（如业务容器 + 日志收集 Sidecar 容器）。
*   **共享网络与存储**：同一个 Pod 内的容器共享网络命名空间（共享同一个 IP 和端口），可以通过 `localhost` 互相访问；可以共享挂载的存储卷。
*   **设计哲学**：Pod 相当于虚拟机中的“进程组”，K8s 调度的不是单个容器，而是一个完整的业务运行环境。

### 10.3 K8s 核心组件（架构级理解）
*   **Control Plane（控制面，大脑）**：
    *   **kube-apiserver**：所有请求的统一入口，负责认证和通信。
    *   **etcd**：高可用键值存储数据库，保存 K8s 的所有状态（唯一的事实来源）。
    *   **kube-scheduler**：负责决定新创建的 Pod 该分配到哪台节点上（打分机制）。
    *   **kube-controller-manager**：负责执行各种控制器逻辑（如 Deployment 控制副本数）。
*   **Worker Node（工作节点，干活的）**：
    *   **kubelet**：节点上的“包工头”，负责和 apiserver 通信，管理 Pod 的生命周期。
    *   **kube-proxy**：负责维护节点的网络规则（如 iptables），实现 Service 的负载均衡。
    *   **Container Runtime**：容器运行时（如 containerd、Docker），负责真正的拉取镜像和运行容器。

## 11. K8s 经典故障排障：CrashLoopBackOff 实战

### 11.1 什么是 CrashLoopBackOff？
容器内部进程崩溃退出后，K8s 默认会尝试重启它。但由于连续重启失败，K8s 触发了指数级退避机制（Back-off），导致容器一直处于“崩溃-等待重启-再次崩溃”的循环中。

### 11.2 排障标准动作（四步曲）
1.  **看事件（宏观）**：
    `kubectl describe pod <pod-name>`
    查看最下方的 `Events` 列表，关注是否有 `OOMKilled`、`Liveness probe failed`、`FailedMount` 等关键字。
2.  **看日志（微观）**：
    `kubectl logs <pod-name>`
    如果容器反复重启，使用 `kubectl logs <pod-name> -p`（`--previous`）查看上一次崩溃前的应用输出，最常抓到代码报错栈（Traceback）。
3.  **看配置（检查）**：
    检查 Deployment 的 YAML，确认环境变量（Env）、挂载卷（Volume/ConfigMap）是否有误。
4.  **看资源（兜底）**：
    `kubectl top pod` 查看是否触发了资源限制限制（Limits）被 OOM 强杀。

### 11.3 常见原因举例
*   **代码 Bug**：启动时抛异常退出（需查看日志修改代码）。
*   **配置错误**：缺少环境变量、连不上数据库。
*   **探针失败**：Readiness/Liveness 探针配置过于严格，应用还没启动完就被 K8s 判定为死掉并强杀。
*   **内存溢出**：设置的 Memory Limit 太小，应用稍微一跑就超过限额被系统杀掉。

## 12. K8s Service 服务发现与负载均衡原理

### 12.1 为什么需要 Service？
*   **痛点**：Pod 是有生命周期的，销毁重建后 IP 会变化。如果直接用 Pod IP 通信，应用将极其脆弱。
*   **Service 的作用**：为一组提供相同功能的 Pod 提供一个**稳定的虚拟 IP（ClusterIP）**和**统一的访问入口**。

### 12.2 Service 的底层实现机制
1.  **Label Selector**：Service 通过标签选择器（如 `app: my-python-app`）动态匹配后端的 Pod。
2.  **Endpoints**：K8s 会自动维护一个与 Service 同名的 Endpoints 对象，里面实时记录着所有健康 Pod 的真实 IP 和端口。
3.  **kube-proxy 与 iptables**：Service 的虚拟 IP 实际上是一个“假 IP”。真正的转发工作由每个节点上的 `kube-proxy` 完成。它会在节点内核里写入 **iptables 规则**。当流量到达虚拟 IP 时，内核直接通过规则把目标地址 **DNAT**（目标地址转换）为某个真实的 Pod IP。

### 12.3 Service 的四种类型
*   **ClusterIP**：默认类型，分配一个集群内部虚拟 IP，仅供集群内 Pod 互相访问。
*   **NodePort**：在每个宿主机上开放一个随机端口（30000-32767），外部可通过 `宿主机IP:NodePort` 访问。
*   **LoadBalancer**：通常配合云厂商的负载均衡器（如阿里云 SLB）使用，分配公网 IP。
*   **ExternalName**：将 Service 映射到外部的 DNS 域名。

## 13. K8s 配置管理：ConfigMap 与 Secret

### 13.1 为什么需要配置分离？
*   **痛点**：把配置（如数据库密码、环境变量）硬编码在代码或镜像中，会导致严重的安全隐患（代码泄露导致库被删），且违背了“一次构建，到处运行”的容器原则。
*   **K8s 解法**：将配置从镜像中抽离，以挂载卷（Volume）或环境变量（Env）的形式在运行时注入。

### 13.2 ConfigMap（非敏感配置）
*   **用途**：存储明文配置数据（如 HTML 文件、Nginx 配置、普通环境变量）。
*   **使用方式**：
    1. 作为环境变量注入（`envFrom`）。
    2. 作为文件挂载到容器中（`volumeMounts`）。修改 ConfigMap 后，挂载的文件会自动更新（有延迟），但环境变量不会自动更新，需重启 Pod。

### 13.3 Secret（敏感配置）
*   **用途**：存储密码、Token、证书等敏感信息。
*   **注意**：Secret 默认使用 **Base64 编码**（这不是加密，只是防止肉眼直接看到）。生产环境建议开启 K8s 的 **ETCD 静态加密**，并严格配置 RBAC 权限，防止普通用户查看到 Secret 内容。
*   **使用方式**：与 ConfigMap 相同，支持环境变量注入和文件挂载。

## 14. K8s 存储机制与数据持久化

### 14.1 为什么需要数据持久化？
*   容器的文件系统是**临时的（Ephemeral）**。Pod 重启或重建后，容器内部写入的文件会丢失。
*   为了保存数据库数据、用户上传的图片、日志等，必须将数据存储在 Pod 生命周期之外的存储中。

### 14.2 核心概念：PV、PVC 与 StorageClass
*   **Volume（存储卷）**：Pod 级别的存储挂载方式，可解决同一 Pod 内多个容器共享数据的问题，但 Pod 死后依然会丢失（取决于后端存储类型）。
*   **PV（Persistent Volume，持久卷）**：集群管理员提供的真实存储资源（如阿里云云盘、NFS 共享目录），独立于任何 Pod。
*   **PVC（Persistent Volume Claim，持久卷声明）**：用户（开发者）向 K8s 申请存储的“声明单”。K8s 会自动寻找匹配的 PV 绑定给 PVC。
*   **StorageClass（存储类）**：动态供给（Dynamic Provisioning）机制。用户只需创建 PVC 并指定 StorageClass，K8s 就会自动去云厂商动态创建一块云盘并绑定为 PV，无需人工预先创建。
*   **访问模式**：
    *   `ReadWriteOnce (RWO)`：单节点读写（大多数云盘支持）。
    *   `ReadOnlyMany (ROX)`：多节点只读。
    *   `ReadWriteMany (RWX)`：多节点读写（需 NFS/Ceph 等共享存储支持）。

### 14.3 实战应用
*   **无状态应用（Stateless）**：如前端 Nginx、Python 后端。代码由镜像提供，数据存外部数据库/对象存储，Pod 随时可销毁重建。
*   **有状态应用（StatefulSet）**：如 MySQL、Redis 集群。必须结合 PVC 与稳定的网络标识（Headless Service）使用，保证每个 Pod 拥有独立的持久存储和数据。

## 15. K8s 外部访问：Ingress 与负载均衡原理

### 15.1 4 层负载均衡 vs 7 层负载均衡
*   **4 层（传输层）**：工作在 TCP/UDP 层。根据 IP 和端口进行转发。代表组件：LVS、阿里云 SLB、K8s NodePort。速度快，但无法解析 HTTP 内容。
*   **7 层（应用层）**：工作在 HTTP/HTTPS 层。能解析 HTTP 报文，根据域名（Host）、URL 路径（Path）、请求头进行精细化路由。代表组件：Nginx、Traefik、HAProxy。

### 15.2 K8s 中的 Ingress 机制
*   **Ingress 资源**：是一份声明式的 YAML 规则（通讯录）。它本身不处理流量，只定义“什么样的请求，该转发给哪个 Service”。
*   **Ingress Controller**：真正干活的组件（如 K3s 默认的 Traefik）。它通过监听 K8s API，实时读取 Ingress 规则，并动态更新自己的反向代理配置。
*   **请求流转链路**：`公网用户 -> 阿里云 ECS 宿主机 (80端口) -> svclb-traefik (iptables) -> Ingress Controller (Traefik Pod) -> Service (ClusterIP) -> Pod (应用)`。

### 15.3 为什么生产环境强烈推荐 Ingress？
1.  **端口收敛**：只需暴露宿主机 80/443 端口，避免开放大量 30000+ 的 NodePort。
2.  **统一网关**：可以做全站 HTTPS 证书配置、限流、黑白名单、灰度发布等高级网关功能。

## 16. Ingress 路由规则解析与分层验证

### 16.1 YAML 配置通俗解析
在 Ingress 的 `rules` 配置中，核心是定义 `path` (路径) 和 `backend` (后端服务)。
*   `path: /`：匹配所有根路径及子路径。
*   `pathType: Prefix`：前缀匹配模式，只要 URL 以该字段开头即触发转发。
*   `backend`：告诉 Ingress Controller（如 Traefik），一旦匹配成功，将流量转发给指定的 Service（如 `frontend-service`）及其端口。

### 16.2 多层路由转发链路
当用户请求到达时，流转链路如下：
1.  **宿主层**：请求到达公网 IP 的 80 端口，被 `svclb-traefik` 劫持。
2.  **网关层**：Traefik 读取 Ingress 规则，根据 URL 路径匹配。
3.  **服务层**：Traefik 将请求转发给对应的 Service (ClusterIP)。
4.  **Pod 层**：Service 根据 iptables/ipvs 规则，将流量负载均衡到具体的 Pod IP 和容器端口。

### 16.3 运维验证手段
*   `curl -s http://127.0.0.1/`：验证根路径是否能正确匹配到前端。
*   `curl -s http://127.0.0.1/api`：验证特定路径是否能正确匹配到后端。
*   结合 `tcpdump` 抓包，可直观看到应用层的 HTTP 请求路径（如 `GET /api HTTP/1.1`）在到达后端前的真实面貌。

## 17. K8s 核心机制：自愈与滚动更新

### 17.1 自愈机制 (Self-healing)
*   **声明式 API**：用户只定义“期望状态”（如 Deployment 的 replicas=3），而不去执行具体的启动命令。
*   **控制器循环 (Reconciliation Loop)**：K8s 内部的 Controller 不断比对“当前状态”与“期望状态”。如果当前 Pod 数量少于期望值（如因为节点宕机或手动误删），Controller 会立刻触发重建，确保业务永远符合期望状态。

### 17.2 滚动更新 (Rolling Update)
*   **痛点**：传统升级需要停机（停机更新），导致服务中断。
*   **机制**：Deployment 升级时，K8s 会新建一个 ReplicaSet（新版），逐渐增加新 Pod 数量，同时逐渐减少旧 Pod 数量。
*   **关键参数**：
    *   `maxSurge`：更新过程中，最多允许超出期望 Pod 数的数量（默认 25%）。
    *   `maxUnavailable`：更新过程中，最多允许有多少个 Pod 处于不可用状态（默认 25%）。如果设为 0，则实现零停机（需资源充足）。

### 17.3 版本回滚 (Rollback)
*   K8s 的每一次更新都会生成一条 Revision 记录。
*   当新版本出现故障时，使用 `kubectl rollout undo deployment/<name>` 即可瞬间回滚到上一个健康的版本，极大地提高了发布容错率。

## 18. 分布式微服务高可用：熔断、降级与限流

### 18.1 什么是雪崩效应？
在微服务链路中（A -> B -> C），如果服务 C 出现故障导致响应缓慢，服务 B 的线程池会被耗尽，进而导致服务 A 崩溃，最终引发整个系统瘫痪。

### 18.2 核心防御机制
*   **熔断（Circuit Breaking）**：
    *   类似电路保险丝。当某个下游服务的失败率达到阈值（如 50%）时，主动切断调用，直接返回错误，不再让请求堆积。
    *   保护自身不被拖死，待下游恢复后再半开试探。
*   **降级（Degradation）**：
    *   当某个非核心服务不可用时，提供兜底方案（Fallback）。
    *   例如：评价服务挂了，直接返回“暂无评价”，确保主流程（商品详情、下单）正常进行。属于“丢车保帅”。
*   **限流（Rate Limiting）**：
    *   在网关或服务入口限制单位时间内的并发请求数（如 QPS）。
    *   常用算法：令牌桶（Token Bucket）、漏桶（Leaky Bucket）、滑动窗口。
    *   超出阈值的请求直接被拒绝（429 Too Many Requests），保护后端不被海量请求击垮。

## 19. 云原生可观测性：日志收集架构

### 19.1 为什么容器日志不能直接看？
*   容器的文件系统是临时的，Pod 销毁后，日志随之丢失。
*   节点数量多，业务 Pod 飘移，无法通过单一服务器登录排查。
*   需要集中检索、监控报警、长期留存以满足合规要求。

### 19.2 主流日志收集架构（EFK / ELK）
*   **Fluentd / Filebeat (采集端)**：通常以 **DaemonSet** 形式部署在每个 Node 上。通过挂载宿主机的 `/var/log/containers` 目录（HostPath），实时读取所有容器的日志。
*   **Elasticsearch / Loki (存储与索引端)**：负责日志的集中存储和快速检索。
*   **Kibana / Grafana (展示端)**：提供图形化界面，支持关键字搜索、日志聚合分析和报警配置。

### 19.3 Pod 日志采集的三种模式
1.  **Node 级采集 (DaemonSet)**：最常用。每个节点跑一个采集器，收集该节点上所有容器的标准输出日志。
2.  **Sidecar (边车模式)**：在业务 Pod 里额外跑一个日志采集容器，专门处理该 Pod 内业务容器的日志（适合多行日志、特殊格式）。
3.  **推送到远端**：应用代码直接把日志推送到 Kafka 等消息队列，与 K8s 平台解耦。

### 19.4 可观测性三大支柱 (Observability)
*   **Logs (日志)**：发生了什么（离散的文本记录）。
*   **Metrics (指标)**：系统状态如何（CPU、内存、QPS、延迟，如 Prometheus + Grafana）。
*   **Traces (链路追踪)**：请求在微服务间流转经过了哪些节点，哪里耗时最长（如 Jaeger、SkyWalking）。

## 20. Docker 镜像瘦身与安全优化

### 20.1 为什么要瘦身？
*   **提高部署速度**：镜像越小，K8s 节点拉取镜像（Pod 启动）的速度越快。
*   **节省存储空间**：减少容器镜像仓库（如 Harbor）和宿主机磁盘的占用。
*   **减少安全漏洞**：系统底层的工具越少，被黑客利用的漏洞（CVE）就越少。

### 20.2 瘦身核心手段
1.  **选择精简基础镜像**：
    *   避免使用 `ubuntu:latest`（将近 80MB）。
    *   优先使用 `alpine`（仅 5MB），或特定语言官方的 `slim` 版本。
    *   （极限做法：使用 `scratch` 空白镜像，仅适用于静态编译语言如 Go/Rust）。
2.  **多阶段构建 (Multi-stage Build)**：
    *   在 `builder` 阶段使用完整镜像编译代码。
    *   在 `runner` 阶段只 `COPY --from=builder` 需要的产物（如二进制文件或编译好的依赖），彻底抛弃编译器和构建缓存。
3.  **减少镜像层数**：
    *   将 `RUN` 命令用 `&&` 连接，清理包管理器缓存（如 `apt clean`、`rm -rf /var/lib/apt/lists/*`、`--no-cache`）。

### 20.3 镜像安全最佳实践
*   **非 Root 运行**：在 Dockerfile 中创建普通用户并 `USER` 切换，避免容器拥有宿主机 Root 权限。
*   **使用 .dockerignore**：忽略 `.git`、`node_modules` 等不必要文件。
*   **镜像扫描**：使用 Trivy 等工具扫描镜像漏洞。

## 21. Linux 目录与文件结构查看命令

### 21.1 查看目录结构
*   `ls`：列出当前目录下的文件（不包含隐藏文件）。
*   `ls -l`：以长列表格式显示详细信息（权限、所有者、大小、修改时间）。
*   `ls -a`：显示所有文件，包含以 `.` 开头的隐藏文件（如 `.git`）。
*   `ls -R`：递归列出所有子目录下的文件。
*   `tree`：以树状图形式展示目录结构（需安装：`apt install tree`）。可配合 `-L 2` 限制显示层级。

### 21.2 查找与定位
*   `pwd`：显示当前所在的工作目录的绝对路径。
*   `find /path -name "*.yaml"`：在指定目录下按文件名查找文件。

## 23. 云原生 CI/CD 自动化流水线

### 23.1 什么是 CI/CD？
*   **CI (Continuous Integration)**：持续集成。开发者频繁地将代码推送到远端仓库，系统自动执行构建、测试，尽早发现集成错误。
*   **CD (Continuous Delivery/Deployment)**：持续交付/部署。将通过测试的代码自动发布到生产环境，实现快速交付。

### 23.2 基于 GitHub Actions 的极简流水线实战
*   **触发条件**：`on: push: branches: [ "main" ]`，只要 main 分支有代码推入，流水线自动启动。
*   **安全认证**：将服务器的 SSH 私钥存入 GitHub Secrets（`SERVER_SSH_KEY`），通过 `appleboy/ssh-action` 动作免密登录云服务器。
*   **自动化脚本**：登录服务器后，自动执行 `git pull` -> `docker build` -> `docker save` 导入 K3s -> `kubectl rollout restart`。全程无需人工干预。

### 23.3 企业级 CI/CD 进阶方向
*   **镜像仓库 (Harbor / ACR)**：GitHub Actions 本地构建镜像后，不应该直接导给单机，而是 `docker push` 到私有镜像仓库。K8s 集群通过 `kubectl set image` 拉取最新镜像。
*   **GitOps (ArgoCD / Flux)**：更高级的部署模式。将 K8s 的 YAML 也放到 Git 仓库里，集群内的 ArgoCD 自动监听仓库变化，自动同步集群状态。
